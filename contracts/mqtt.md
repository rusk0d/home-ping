## Broker and connection settings

| Setting | Firmware (all 3 nodes) | Backend (`server.py`) | Web (`index.html`) |
|---|---|---|---|
| Library | PubSubClient | paho-mqtt 2.1.0 (`mqtt.Client()`) | mqtt.js 5.16.0 from unpkg (pinned) |
| Host / port | `MQTT_BROKER` / `MQTT_PORT` from `secrets.h` (template: 1883, plain TCP) | `localhost:1883`, hard-coded | `MQTT_CONFIG.url` from `web/config.js` (WebSockets) |
| Auth | `MQTT_USER` / `MQTT_PASS` from `secrets.h` | `MQTT_USER` / `MQTT_PASS` from `.env` | `MQTT_CONFIG.username` / `.password` (CLAUDE.md says this is a read-only user) |
| Client ID | `<DEVICE_NAME>_<efuse MAC hex>` | auto-generated by paho | auto-generated by mqtt.js |
| Keep-alive | 60 s (`setKeepAlive(60)`) | paho default (60 s) | mqtt.js default (60 s) |
| Clean session | PubSubClient default (true) | paho default (true) | mqtt.js default (true) |
| Last will (LWT) | **none** set (`connect(id, user, pass)` has no will args) | none | none |
| Publish QoS | 0 (PubSubClient can only publish at QoS 0) | 0, only `home/backend/occupancy_hourly` | does not publish |
| Subscribe QoS | n/a | 0 (`client.subscribe(TOPIC)`, default) | 0 (default) |

There are **no status, availability or last-will topics**. The backend decides
whether a device is online from the `devices.last_seen` timestamp in the DB
(see `api.md`, `HEARTBEAT_TIMEOUT` = 120 s).

## Topic summary

| Topic | Publisher(s) | Subscriber(s) | Interval | Retained | QoS |
|---|---|---|---|---|---|
| `home/esp32/bme280` | main_node (`home_ping_esp32`) | backend (via `home/esp32/#`), web page | 30 s | yes | 0 |
| `home/esp32/presence` | main_node (`home_ping_esp32`) **and** eink_node (`hallway_presence_esp32`) | backend (via `home/esp32/#`) | 5 s per node | yes | 0 |
| `home/esp32/co2` | co2_node (`co2_sensor_esp32`) | backend (via `home/esp32/#`), web page | 60 s | yes | 0 |
| `home/backend/occupancy_hourly` | backend | web page | 300 s + on every (re)connect | yes | 0 |

### How the backend routes messages

The backend subscribes to `home/esp32/#` and **ignores the topic name**. It
routes on payload keys (`server.py` `on_message`), in this order:

1. Payload has `presence` → presence handler → `presence_readings` table.
2. Anything else → environmental handler → `readings` table.

(A soil handler for `moisture`+`raw` payloads existed until #9; it was removed with the
soil feature because no soil node exists.)

So the topic names are informational only for the backend. A payload's key set
decides how it is stored. Non-JSON payloads raise an exception that is caught
and printed (message dropped).

### Common fields

| Field | Type | Unit | Notes |
|---|---|---|---|
| `device` | string | n/a | Fixed per sketch (`DEVICE_NAME`). Used by the backend as the device ID everywhere. |
| `uptime` | integer | seconds | `millis() / 1000`. Wraps after ~49.7 days (32-bit `millis()`). |
| `rssi` | integer | dBm | `WiFi.RSSI()`. Sent on presence and co2, **not** on bme280. |

## `home/esp32/bme280`

- Publisher: `firmware/main_node` (`DEVICE_NAME = "home_ping_esp32"`), BME280 on I2C.
- Interval: every 30 s (`ENV_INTERVAL = 30000`).
- Retained: yes (`publish(..., true)`). QoS 0.
- Not published at all if the BME280 failed to initialise or a read returned NaN.
  Readings are skipped silently, so no null fields are ever sent.

| Field | Type | Unit | Notes |
|---|---|---|---|
| `device` | string | n/a | `"home_ping_esp32"` |
| `temp_c` | float | °C | `readTemperature() + TEMP_OFFSET` (offset currently 0.0) |
| `humidity` | float | %RH | |
| `pressure` | float | hPa | `readPressure() / 100` |
| `uptime` | integer | s | |

Example:

```json
{"device":"home_ping_esp32","temp_c":22.41,"humidity":48.3,"pressure":1013.62,"uptime":86400}
```

Backend handling: env handler. Stores `temp_c` → `readings.temp`, `humidity`,
`pressure`, `uptime`. Runs humidity and temperature alert checks (see
`notifications.md`). Float precision on the wire is ArduinoJson's default
(**UNCERTAIN**: exact number of decimals).

## `home/esp32/presence`

- Publishers (two devices share this topic):
  - `firmware/main_node`: `DEVICE_NAME = "home_ping_esp32"` (backend treats this as "main room")
  - `firmware/eink_node`: `DEVICE_NAME = "hallway_presence_esp32"` (backend treats this as "hallway")
- Sensor: LD2410C mmWave radar.
- Interval: every 5 s per node (`PRESENCE_INTERVAL = 5000`). On the eink node,
  publishes can be delayed while the e-paper refreshes and the BKK fetch runs
  (blocking, up to ~10 s HTTP timeout plus display refresh) once a minute.
- Retained: yes. QoS 0.

| Field | Type | Unit | Notes |
|---|---|---|---|
| `device` | string | n/a | `"home_ping_esp32"` or `"hallway_presence_esp32"` |
| `radar_connected` | bool | n/a | `radar.isConnected()` |
| `presence` | bool | n/a | `radar.presenceDetected()` |
| `stationary` | bool | n/a | stationary target detected |
| `moving` | bool | n/a | moving target detected |
| `distance` | integer | cm (**UNCERTAIN**: ld2410 library units, believed cm) | Stationary target distance if `stationary`, else moving target distance if `moving`, else 0 |
| `signal` | integer | 0–100 energy (**UNCERTAIN**: library scale) | Same selection rule as `distance` |
| `rssi` | integer | dBm | |
| `uptime` | integer | s | |

Example:

```json
{"device":"hallway_presence_esp32","radar_connected":true,"presence":true,"stationary":true,"moving":false,"distance":142,"signal":37,"rssi":-61,"uptime":3605}
```

Backend handling: presence handler (key `presence` present). Derives
`occupied = moving OR (stationary AND signal >= 15)` and stores the row in
`presence_readings`. Runs the radar-offline and occupancy-arrival alert
checks (see `notifications.md`). Missing fields default to: `presence`/`stationary`/`moving` = false,
`distance`/`signal`/`rssi`/`uptime` = 0, `radar_connected` = **true**, `device` = `"home_ping_esp32"`.

## `home/esp32/co2`

- Publisher: `firmware/co2_node` (`DEVICE_NAME = "co2_sensor_esp32"`), MH-Z19C on UART1.
- Interval: every 60 s (`PUBLISH_INTERVAL = 60000`). The first publish happens
  as soon as the loop starts. Readings are flagged invalid for the first 180 s
  (`WARMUP_MS`).
- Retained: yes. QoS 0.
- `co2` and `sensor_tmp` are **only present when the reading is valid**
  (`err == RESULT_OK && !warming && 0 < co2 <= 5000`). Otherwise the keys are omitted.

| Field | Type | Unit | Always present | Notes |
|---|---|---|---|---|
| `device` | string | n/a | yes | `"co2_sensor_esp32"` |
| `co2_ok` | bool | n/a | yes | true when the reading is valid (rule above) |
| `warming` | bool | n/a | yes | `millis() < 180000` |
| `err` | integer | n/a | yes | MH-Z19 library `errorCode` (**UNCERTAIN**: `RESULT_OK` is 1 in the WifWaf MHZ19 library) |
| `rssi` | integer | dBm | yes | |
| `uptime` | integer | s | yes | |
| `co2` | integer | ppm | only if valid | 1–5000 |
| `sensor_tmp` | integer | °C | only if valid | MH-Z19 internal temperature, coarse, not room temperature |

Example (valid):

```json
{"device":"co2_sensor_esp32","co2_ok":true,"warming":false,"err":1,"rssi":-58,"uptime":7260,"co2":812,"sensor_tmp":24}
```

Example (warming up):

```json
{"device":"co2_sensor_esp32","co2_ok":false,"warming":true,"err":1,"rssi":-58,"uptime":60}
```

Backend handling: env handler (no `presence`). Stores a
`readings` row with `co2` (NULL when absent), `uptime`; `temp`, `humidity` and
`pressure` are NULL. Stores `co2_ok` in `readings.co2_ok` (1/0, NULL when the message
has none) and serves it via `/api/latest_all`. Temp/humidity alerts are
skipped because `temp_c` and `humidity` are absent.

## `home/backend/occupancy_hourly`

- Publisher: `backend/server.py` (`publish_hourly_occupancy()`), using the backend's
  `MQTT_USER`. The broker ACL must allow that user to publish here, and the web
  page's read-only user to subscribe.
- Interval: every 300 s (`OCCUPANCY_HOURLY_INTERVAL`) from a background thread,
  plus once in `on_connect` (startup and every reconnect).
- Retained: yes, so a new subscriber gets today's chart immediately. QoS 0.
- Outside `home/esp32/#`, so the backend doesn't receive its own messages.
- Same data as the occupancy part of `GET /api/hourly`: `presence_readings` for
  `PRESENCE_DEVICE` (`home_ping_esp32`) only, since **local midnight**.

| Field | Type | Unit | Notes |
|---|---|---|---|
| `device` | string | n/a | `PRESENCE_DEVICE` (`"home_ping_esp32"`) |
| `date` | string | n/a | `YYYY-MM-DD`, server local date |
| `updated` | string | n/a | `YYYY-MM-DD HH:MM:SS`, server local time of this publish |
| `hours` | array | n/a | one entry per hour from `00:00` to the current hour, oldest first |
| `hours[].hour` | string | n/a | `HH:00` |
| `hours[].occupancy` | integer or null | % | mean(`occupied`)×100, rounded. `null` = no radar rows that hour (unlike `/api/hourly`, which omits the hour) |

Example:

```json
{"device":"home_ping_esp32","date":"2026-10-14","updated":"2026-10-14 20:55:34",
 "hours":[{"hour":"00:00","occupancy":0},{"hour":"01:00","occupancy":null},{"hour":"20:00","occupancy":75}]}
```

## Web page (`web/index.html`) as a subscriber

- Subscribes to `home/esp32/bme280`, `home/esp32/co2` and `home/backend/occupancy_hourly`
  only (read-only user).
- occupancy_hourly: 24-slot bar chart for today. `null` hours are shown as "no data", hours
  after the last entry as future. Greyed out if `updated` is over 15 min old or `date` isn't
  the browser's local date. `updated` is parsed as browser local time (same timezone assumed).
- bme280: shows `temp_c`, `humidity`, `pressure`, `uptime`.
- co2: shows `co2` only when `co2_ok` is true and `co2` is present; otherwise
  shows "warming up" (`warming`) or "no valid reading" (`err`). Also shows `uptime`, `rssi`.
- History and sparklines are in browser memory only, timestamped with the
  browser's receive time. Retained messages (`packet.retain`) are labelled
  "last known value" instead of "just now".
- A card is greyed out as stale after 90 s (bme280) or 180 s (co2) without a message.
- `home/esp32/dht11` (an old, unpublished topic) is no longer used.

## Mismatches and issues between components

1. ~~**Web page listens on a dead topic.**~~ Fixed in #2: `web/index.html` now
   subscribes to `home/esp32/bme280` and `home/esp32/co2` instead of `home/esp32/dht11`.
2. **Two devices publish retained messages to `home/esp32/presence`.** The broker
   keeps one retained message per topic, so a new subscriber gets only
   whichever node published last. The backend tells the nodes apart by
   `device`, so storage is fine, but the topic doesn't identify the
   device on its own.
3. **Retained messages are replayed into the backend on every (re)connect.**
   All three publishers set retain=true. When the backend restarts or
   reconnects, it receives the last message on each topic and stores it as a
   new row with the *current* timestamp (the payload has no timestamp). The
   in-memory notification cooldowns are also reset on restart, so a replayed
   message can trigger an immediate alert (see `notifications.md`).
4. **No timestamps in payloads.** Every stored `ts` is the backend's receive
   time (server local time). Delayed or replayed messages get the wrong time.
5. **No LWT / status topic.** Offline detection relies on `devices.last_seen`
   plus the 120 s `HEARTBEAT_TIMEOUT`. A node that drops off is only noticed
   when the REST API is next queried.
6. **`uptime` wraps at ~49.7 days.** `millis()/1000` wraps on main_node and co2_node,
   which have no scheduled reboot. The backend's restart detector
   (`note_uptime`, drop > 120 s) will log a false `RESTART` event when that
   happens. eink_node reboots every 12 h, so it's not affected.
7. **main_node reports `uptime` on two topics.** The same device ID sends `uptime` on both
   `presence` and `bme280`. The backend's `LAST_UPTIME` per device mixes the two
   streams. The 120 s tolerance hides this, since both come from the same
   `millis()`.
8. **Fields sent but not stored or used by the backend:**
   - co2: `warming`, `err`, `rssi`, `sensor_tmp` are dropped. `co2_ok` is stored in `readings`.
   - bme280: all fields are used.
   - presence: all fields are stored.
9. **Fields the backend reads that no firmware sends:**
   - `server.py` comments mention "PIR occupied fields from other devices are
     ignored". No current firmware sends PIR fields.
10. **Backend defaults hide malformed messages.** A presence payload without
    `radar_connected` is treated as connected, and one without `device` is
    attributed to `home_ping_esp32`.
11. **Topic name `bme280` vs device name.** main_node's env data goes to
    `home/esp32/bme280` but is stored under device `home_ping_esp32` (which the
    Android app labels "OLED"/"Ping"). The naming is inconsistent but harmless,
    since the backend ignores topic names.
12. **eink_node also declares API config it never uses.** `API_URL`/`API_USER`/`API_PASS`
    are read from `secrets.h` but nothing references them (**UNCERTAIN**: a
    leftover from fetching `/api/latest` for the display). Not an MQTT issue,
    but it means `secrets.h` must define them for the sketch to compile.
13. **Firmware build issues seen while reading (not contract issues, noted for completeness):**
    `eink_node.ino:32` is missing a `;` after `BKK_URL`. All three sketches
    do `const char* WIFI_SSID = WIFI_SSID;` etc., which redeclares the
    `const char* const` names that `secrets.example.h` defines. That only
    compiles if the real `secrets.h` uses `#define` macros instead
    (**UNCERTAIN**: the real `secrets.h` wasn't read).
