# MQTT contract

Topics and payloads between the ESP32 nodes (`firmware/`), the backend (`backend/ingest.py`)
and the web page (`web/index.html` + `app.js`).
It is the source of truth: update it in the same change as the code (see CLAUDE.md).
First written on 2026-10-13 by reading the code; anything still marked **UNCERTAIN** was
inferred then and hasn't been confirmed since.

## Web users (since #99)

The web page has no shared account any more: each person signs in with their own
Mosquitto account. `web/config.js` holds only `url`. The page keeps the login only after
the broker accepted it (sessionStorage, or localStorage with "remember me"), and shows
the login form again on CONNACK 4/5 (bad user name or password / not authorized).

Each web user needs a password-file entry and a read-only ACL entry on the broker:

```
sudo mosquitto_passwd /etc/mosquitto/passwd <name>      # add or change a user
sudo mosquitto_passwd -D /etc/mosquitto/passwd <name>   # remove a user

# /etc/mosquitto/acl
user <name>
topic read home/esp32/#
topic read home/backend/#
```

Then `sudo systemctl restart mosquitto`. `home/esp32/#` covers the env, CO2, presence
and status topics the page subscribes to; `home/backend/#` covers `occupancy_hourly` and `history_24h`.

## Broker accounts (since #31)

Every client has its own Mosquitto account with only the access it needs. The shared
`esp32` account (read/write on `home/#`, leaked through the old `config.js`) and the old shared
read-only `web` account (from before #99) were deleted on 2026-10-16.

| Account | Used by | ACL (`/etc/mosquitto/acl`) |
|---|---|---|
| `sensor` | both nodes (`MQTT_USER` in `secrets.h`) | `topic write home/esp32/#` (publish only, also covers the last will) |
| `backend` | the backend (`MQTT_USER` in `/opt/iot/.env`) | `topic read home/esp32/#`, `topic write home/backend/#` |
| one per person (e.g. `david`) | the web page's login form (#99) | `topic read home/esp32/#`, `topic read home/backend/#` (see "Web users") |

`per_listener_settings true`: each listener has its own `password_file` and `acl_file` line
pointing to the same files.
- 8883 (MQTT over TLS, #31), public: the nodes connect from home. `certfile`/`keyfile` are
  copies of the web server's Let's Encrypt certificate (`ruskodavid.hu`) in
  `/etc/mosquitto/certs/`, made by the certbot deploy hook
  `/etc/letsencrypt/renewal-hooks/deploy/mosquitto.sh` (copies them on each renewal and
  restarts Mosquitto; the nodes reconnect by themselves).
- 1883 (plain MQTT), localhost only (`listener 1883 127.0.0.1`): the backend.
- 9001 (WebSockets): nginx `/mqtt` is its only client. The config says
  `listener 9001 127.0.0.1` (#169), but Mosquitto 2.0.11 with Ubuntu's libwebsockets 4.0
  binds websockets listeners to all interfaces anyway (`*:9001`), with `bind_interface lo`
  too (tested 2026-10-17, #208). **ufw keeps 9001 closed**: never `ufw allow 9001`.
Add users with `mosquitto_passwd /etc/mosquitto/passwd <name>` (never `-c`, which wipes the
file), edit the ACL with `printf`/an editor, then `systemctl restart mosquitto`. The nodes
reconnect within a keep-alive interval, the backend at once.

## Broker and connection settings

| Setting | Firmware (main_node, eink_node) | Backend (`ingest.py`, `server.py`) | Web (`app.js`) |
|---|---|---|---|
| Library | PubSubClient, via the HomePing library (#75) | paho-mqtt 2.1.0, callback API v2 (#66) | mqtt.js 5.16.0 from unpkg (pinned, with SRI, #62) |
| Host / port | `MQTT_BROKER` / `MQTT_PORT` from `secrets.h`: the certificate's host name, 8883 | `localhost:1883`, hard-coded | `MQTT_CONFIG.url` from `web/config.js` (WebSockets) |
| TLS | `WiFiClientSecure`, trusts ISRG Root X1 and Root YR (`HomePingTls.h`), checks the host name; certificate dates not checked (no clock needed) | none (localhost) | `wss://` through nginx |
| Auth | `MQTT_USER` / `MQTT_PASS` from `secrets.h`: account `sensor` | `MQTT_USER` / `MQTT_PASS` from `.env`: account `backend` | each person's own read-only account, typed into the page's login form (since #99; see "Web users") |
| Client ID | `<DEVICE_NAME>_<efuse MAC hex>` | auto-generated by paho | auto-generated by mqtt.js |
| Keep-alive | 60 s (`setKeepAlive(60)`) | paho default (60 s) | mqtt.js default (60 s) |
| Clean session | PubSubClient default (true) | paho default (true) | mqtt.js default (true) |
| Last will (LWT) | `offline`, retained, QoS 1 on `home/esp32/<device>/status`; `online` published on connect (#13) | none | none |
| Publish QoS | 0 (PubSubClient can only publish at QoS 0) | 0, only `home/backend/occupancy_hourly` and `home/backend/history_24h` | does not publish |
| Subscribe QoS | n/a | 0 (`client.subscribe(TOPIC)`, default) | 0 (default) |

The nodes announce themselves on `home/esp32/<device>/status` (see below), but the backend
still decides whether a device is online from the `devices.last_seen` timestamp in the DB
(see `api.md`, `HEARTBEAT_TIMEOUT` = 120 s) and the offline alerts from data (#13).

### How the backend routes messages

The backend subscribes to `home/esp32/#` and **ignores the topic name**.
Messages delivered with the **retain flag** are skipped entirely (since #5): those
are the broker replaying the last retained message of each topic on (re)subscribe,
i.e. old readings. Live messages arrive with the flag cleared (MQTT 3.1.1). The
firmware keeps publishing with retain for the web page.

Other messages are routed on payload keys (`server.py` `on_message`), in this order:

1. Payload has `presence` → presence handler → `presence_readings` table.
2. Anything else → environmental handler → `readings` table.

(A soil handler for `moisture`+`raw` payloads existed until #9; it was removed with the
soil feature because no soil node exists.)

So the topic names are informational only for the backend. A payload's key set
decides how it is stored. Malformed payloads (not valid UTF-8, not JSON, not a JSON
object) are logged as `MQTT error: …` and dropped. Nothing may escape `on_message`:
paho re-raises callback exceptions, which would end its network thread and stop all
ingestion (#58).

### Common fields

| Field | Type | Unit | Notes |
|---|---|---|---|
| `device` | string | n/a | Fixed per sketch (`DEVICE_NAME`). Used by the backend as the device ID everywhere. **Required** on `bme280` and `co2`: without it (or not a non-empty string) the backend logs a warning and drops the message (#170; before, it stored it as device `"esp32"`). |
| `uptime` | integer | seconds | Seconds since boot, from the 64-bit `esp_timer_get_time()` (`hpUptimeSeconds()` in the shared HomePing library), so it doesn't wrap (#8, #50, #75). Before: `millis() / 1000`, which wrapped after ~49.7 days. |
| `rssi` | integer | dBm | `WiFi.RSSI()`. Sent on presence and co2, **not** on bme280. |

## `home/esp32/bme280`

- Publisher: `firmware/main_node` (`DEVICE_NAME = "home_ping_esp32"`), BME280 on I2C (GPIO 21/22,
  address 0x76 or 0x77). Since the node merge (#57) the main node is the former CO₂ board with the
  radar and BME280 added; during the merge the CO₂ board briefly published it as
  `co2_sensor_esp32`. Same payload either way.
- Interval: every 30 s (`ENV_INTERVAL = 30000`).
- Retained: yes (`publish(..., true)`). QoS 0.
- Not published at all if the BME280 failed to initialise or a read returned NaN.
- The backend drops `temp_c`, `humidity` and `pressure` together (stores them as null, logs a
  warning) if any is outside the BME280's range: −40…85 °C, 0…100 %RH, 300…1100 hPa
  (`config.ENV_VALID`, #57). A disconnected sensor reads e.g. 178 °C / 100 % / −121 hPa.
  Readings are skipped silently, so no null fields are ever sent.

| Field | Type | Unit | Notes |
|---|---|---|---|
| `device` | string | n/a | `"home_ping_esp32"` |
| `temp_c` | float | °C | `readTemperature() + TEMP_OFFSET` (offset currently 0.0) |
| `humidity` | float | %RH | |
| `pressure` | float | hPa | `readPressure() / 100` |
| `uptime` | integer | s | |

Example:

```json
{"device":"home_ping_esp32","temp_c":22.41,"humidity":48.3,"pressure":1013.62,"uptime":86400}
```

Backend handling: env handler. Stores `temp_c` → `readings.temp`, `humidity`,
`pressure`, `uptime`. Runs humidity and temperature alert checks (see
`notifications.md`). Float precision on the wire is ArduinoJson's default
(**UNCERTAIN**: exact number of decimals).

## `home/esp32/presence`

- Publishers (two devices share this topic):
  - `firmware/main_node`: `DEVICE_NAME = "home_ping_esp32"` (backend treats this as "main room")
  - `firmware/eink_node`: `DEVICE_NAME = "hallway_presence_esp32"` (backend treats this as "hallway")
- Sensor: LD2410C mmWave radar.
- Interval: every 5 s per node (`PRESENCE_INTERVAL = 5000`). On the eink node,
  publishes can be delayed while the e-paper refreshes once a minute (a fraction of a
  second; ~2–3 s for the full refresh every 30 min). The BKK fetch runs in its own task
  since #171 and no longer delays them.
- Retained: yes. QoS 0.

| Field | Type | Unit | Notes |
|---|---|---|---|
| `device` | string | n/a | `"home_ping_esp32"` or `"hallway_presence_esp32"` |
| `radar_connected` | bool | n/a | `radar.isConnected()` |
| `presence` | bool | n/a | `radar.presenceDetected()` |
| `stationary` | bool | n/a | stationary target detected |
| `moving` | bool | n/a | moving target detected |
| `distance` | integer | cm (checked on hardware 2026-10-17, #19: 61–469 in one room) | Stationary target distance if `stationary`, else moving target distance if `moving`, else 0 |
| `signal` | integer | 0–100 energy (checked on hardware 2026-10-17, #19) | Same selection rule as `distance` |
| `rssi` | integer | dBm | |
| `uptime` | integer | s | |

Example:

```json
{"device":"hallway_presence_esp32","radar_connected":true,"presence":true,"stationary":true,"moving":false,"distance":142,"signal":37,"rssi":-61,"uptime":3605}
```

Backend handling: presence handler (key `presence` present). Derives
`occupied = moving OR (stationary AND signal >= 15)` and stores the row in
`presence_readings`. Runs the radar-offline and occupancy-arrival alert
checks (see `notifications.md`). Missing fields default to: `presence`/`stationary`/`moving` = false,
`distance`/`signal`/`rssi`/`uptime` = 0, `radar_connected` = **true**, `device` = `"home_ping_esp32"`.

## `home/esp32/co2`

- Publisher: `firmware/main_node` (`DEVICE_NAME = "home_ping_esp32"`) since the node merge (#57),
  MH-Z19C on UART1 (GPIO 25/26). Before: `firmware/co2_node` (`co2_sensor_esp32`), removed.
- `warming` is true for the first 180 s of uptime (`CO2_WARMUP_S`, 64-bit uptime since #119).
- Interval: every 60 s (`CO2_INTERVAL`). The first publish happens as soon as the loop starts.
- Calibration (#167): the sensor's automatic baseline correction (ABC) is **off**; it had made
  the readings go below outdoor level (hourly minima down to 261 ppm). Instead, a manual
  zero-point calibration: run the node ≥20 min in fresh air, then hold the board's BOOT
  button 5 s (or send `calibrate` on serial); the current air becomes 400 ppm. Refused before
  20 min of uptime (LED blinks fast), done = 3 slow blinks. The node also logs it on serial.
- Retained: yes. QoS 0.
- `co2` and `sensor_tmp` are **only present when the reading is valid**
  (`err == RESULT_OK && !warming && 0 < co2 <= 5000`). Otherwise the keys are omitted.

| Field | Type | Unit | Always present | Notes |
|---|---|---|---|---|
| `device` | string | n/a | yes | `"home_ping_esp32"` (before #57: `"co2_sensor_esp32"`) |
| `co2_ok` | bool | n/a | yes | true when the reading is valid (rule above) |
| `warming` | bool | n/a | yes | uptime < 180 s |
| `err` | integer | n/a | yes | MH-Z19 library `errorCode`; `RESULT_OK` = 1 (WifWaf MHZ19 1.5.4 header; a valid reading needs it, #19) |
| `rssi` | integer | dBm | yes | |
| `uptime` | integer | s | yes | |
| `abc` | bool | n/a | yes (since #167) | the MH-Z19's automatic baseline correction as the sensor reports it; should be `false` |
| `co2` | integer | ppm | only if valid | 1–5000 |
| `sensor_tmp` | integer | °C | only if valid | MH-Z19 internal temperature, coarse, not room temperature |

Example (valid):

```json
{"device":"home_ping_esp32","co2_ok":true,"warming":false,"err":1,"rssi":-58,"uptime":7260,"abc":false,"co2":812,"sensor_tmp":24}
```

Example (warming up):

```json
{"device":"home_ping_esp32","co2_ok":false,"warming":true,"err":1,"rssi":-58,"uptime":60,"abc":false}
```

Backend handling: env handler (no `presence`). Stores a
`readings` row with `co2` (NULL when absent), `uptime`; `temp`, `humidity` and
`pressure` are NULL. Stores `co2_ok` in `readings.co2_ok` (1/0, NULL when the message
has none) and serves it via `/api/latest_all`. Temp/humidity alerts are
skipped because `temp_c` and `humidity` are absent. `abc` is not stored (the web page and
`mosquitto_sub` show it).

## `home/esp32/<device>/status` (since #13)

Plain text, not JSON: `online` or `offline`.

- On every MQTT connect each node registers a **last will** on this topic
  (`offline`, retained, QoS 1) and then publishes `online` (retained).
- If the node drops off, the broker publishes the will about 1.5 × keepalive
  (60 s) ≈ 90 s later. Because the client ID is fixed per node, a node that
  reconnects after a short WiFi drop can also trigger the old session's will
  right before its new `online`.
- Backend: logs each live message as an `events` row `STATUS`. `online` counts
  as a sign of life (`touch_device`); `offline` doesn't. The **offline push is
  decided on data age, not on this topic** (see `notifications.md`, `NODE_STATUS`),
  so the reconnect case above doesn't cause false alarms.
- Retained replays are skipped like any other (#5).

## `home/backend/occupancy_hourly`

- Publisher: the backend (`ingest.publish_hourly_occupancy()`), as account `backend`,
  whose ACL allows `write home/backend/#`; the web users read it (see "Broker accounts").
- Interval: every 300 s (`OCCUPANCY_HOURLY_INTERVAL`) from a background thread,
  plus once in `on_connect` (startup and every reconnect).
- Retained: yes, so a new subscriber gets today's chart immediately. QoS 0.
- Outside `home/esp32/#`, so the backend doesn't receive its own messages.
- Same data as the occupancy part of `GET /api/hourly`: `presence_readings` for
  `PRESENCE_DEVICE` (`home_ping_esp32`) only, since **local midnight**.

| Field | Type | Unit | Notes |
|---|---|---|---|
| `device` | string | n/a | `PRESENCE_DEVICE` (`"home_ping_esp32"`) |
| `date` | string | n/a | `YYYY-MM-DD`, server local date |
| `updated` | string | n/a | `YYYY-MM-DD HH:MM:SS`, server local time of this publish |
| `hours` | array | n/a | one entry per hour from `00:00` to the current hour, oldest first |
| `hours[].hour` | string | n/a | `HH:00` |
| `hours[].occupancy` | integer or null | % | mean(`occupied`)×100, rounded. `null` = no radar rows that hour (unlike `/api/hourly`, which omits the hour) |

Example:

```json
{"device":"home_ping_esp32","date":"2026-10-14","updated":"2026-10-14 20:55:34",
 "hours":[{"hour":"00:00","occupancy":0},{"hour":"01:00","occupancy":null},{"hour":"20:00","occupancy":75}]}
```

## `home/backend/history_24h` (since #132)

So the web page's sparklines start with the last day instead of empty.

- Publisher: the backend (`ingest.publish_history_24h()`), as account `backend`; the web
  users read it via `home/backend/#` (no ACL change).
- Interval and retain: like `occupancy_hourly` (both from `ingest.publish_summaries()`):
  every 300 s and on every (re)connect, retained, QoS 0. A failure of one doesn't stop the other.
- Data: hourly averages from `readings`, all devices (like `/api/hourly` without `?device=`),
  for the **last 24 complete hours** (UTC hour boundaries). The current, unfinished hour is
  not included: the page has the live values for it.

| Field | Type | Unit | Notes |
|---|---|---|---|
| `updated` | string | n/a | `YYYY-MM-DDTHH:MM:SSZ`, UTC time of this publish |
| `hours` | array | n/a | only hours with data, oldest first, at most 24 |
| `hours[].start` | string | n/a | start of the hour, `YYYY-MM-DDTHH:00:00Z` (UTC) |
| `hours[].temp` | number or null | °C | mean, 1 dp |
| `hours[].humidity` | number or null | % | mean, 1 dp |
| `hours[].pressure` | number or null | hPa | mean, 1 dp |
| `hours[].co2` | integer or null | ppm | mean, rounded |

`null` = no device reported that value in that hour.

```json
{"updated":"2026-10-16T19:05:00Z",
 "hours":[{"start":"2026-10-15T19:00:00Z","temp":22.4,"humidity":41.2,"pressure":1011.3,"co2":702},
          {"start":"2026-10-16T18:00:00Z","temp":22.9,"humidity":38.0,"pressure":1010.1,"co2":735}]}
```

## Web page (`web/app.js`) as a subscriber

- Subscribes to `home/esp32/bme280`, `home/esp32/co2`, `home/backend/occupancy_hourly`,
  `home/backend/history_24h` (since #132),
  `home/esp32/presence` and `home/esp32/+/status` (read-only user). Topics the broker's ACL
  refuses (SUBACK 128) are logged as a warning in the browser console.
- **Devices list** (#81): one entry per node (main node, hallway radar, CO₂ node, plus any
  unknown `device` that shows up), with uptime, RSSI and state, from all of the topics above:
  - *online* while **live** messages keep coming: limit 30 s for the radar nodes (5 s interval),
    180 s for the CO₂ node. Retained replays update uptime/RSSI but don't prove the node is up.
  - *offline* when the status topic says `offline` (the last will) and nothing newer has
    arrived, or when live data stopped ("no data for …").
  - A retained `online` status counts as online until the first live message.
  - Before the nodes run the #55 firmware there is no status topic, so the state is from data age only.
- occupancy_hourly: 24-slot bar chart for today. `null` hours are shown as "no data", hours
  after the last entry as future. Greyed out if `updated` is over 15 min old or `date` isn't
  the browser's local date. `updated` is parsed as browser local time (same timezone assumed).
- bme280: shows `temp_c`, `humidity`, `pressure`, `uptime`.
- co2: shows `co2` only when `co2_ok` is true and `co2` is present; otherwise
  shows "warming up" (`warming`) or "no valid reading" (`err`). Also shows `uptime`, `rssi`.
- Sparklines (since #132): the hourly averages from `history_24h` (each plotted at the middle
  of its hour) followed by the live readings since the end of its last hour, on a time axis
  from the oldest to the newest point. Each `history_24h` message replaces the hourly points
  and drops the live ones it now covers; live points are kept for at most 24 h. Without
  `history_24h` (older backend) they start empty, as before.
- Live readings and the recent-readings table are in browser memory only, timestamped with
  the browser's receive time. Retained messages (`packet.retain`) are labelled
  "last known value" instead of "just now".
- A card is greyed out as stale after 90 s (bme280) or 180 s (co2) without a message.
- `home/esp32/dht11` (an old, unpublished topic) is no longer used.
- Level thresholds: `co2Level`, `humLevel`, `tempLevel`, a copy of the "Level bands" table in
  `api.md` (#127), which is the place to change them.

## Mismatches and issues between components

1. **Two devices publish retained messages to `home/esp32/presence`** (kept on purpose,
   #10 closed as not planned). The broker keeps one retained message per topic, so a new
   subscriber gets only whichever node published last. That doesn't matter in practice:
   the backend skips retained messages and tells the nodes apart by `device`, and the web
   page's node list fills in at the other node's next reading (~5 s). Hourly occupancy is
   main-room only (`PRESENCE_DEVICE`) by design; the hallway radar mostly sees people
   passing through.
2. **No timestamps in payloads.** Every stored `ts` is the backend's receive
   time (UTC since #65). Delayed messages get the receive time.
3. **main_node reports `uptime` on two topics.** The same device ID sends `uptime` on both
   `presence` and `bme280`. The backend's `LAST_UPTIME` per device mixes the two
   streams. The 120 s tolerance hides this, since both come from the same timer.
4. **Fields sent but not stored or used by the backend:**
   - co2: `warming`, `err`, `rssi`, `sensor_tmp` are dropped. `co2_ok` is stored in `readings`.
   - bme280: all fields are used.
   - presence: all fields are stored.
5. **Fields the backend reads that no firmware sends:** the backend comments mention
   "PIR occupied fields from other devices are ignored". No current firmware sends PIR fields.
6. **Backend defaults hide malformed messages.** A presence payload without
   `radar_connected` is treated as connected, and one without `device` is
   attributed to `home_ping_esp32`. (Env payloads without `device` are dropped since #170.)
7. **Topic name `bme280` vs device name.** main_node's env data goes to
   `home/esp32/bme280` but is stored under device `home_ping_esp32` (which the
   Android app labels "OLED"/"Ping"). The naming is inconsistent but harmless,
   since the backend ignores topic names.
